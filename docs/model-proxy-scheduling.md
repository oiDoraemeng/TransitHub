# 模型路由调度与恢复探测

## 调度顺序

优先级数值越大越优先。只有当前高优先级路由没有可用硬并发容量，或被暂停、被请求策略排除、达到成员 RPM 限制、在当前请求中已失败，才使用下一优先级。

同一优先级内依次使用：

1. 临时 Key 路由：每条软上限 5，优先近期响应头延迟较低的路由。
2. 预置 Key 路由：每条软上限 10，同样参考近期延迟。
3. 两类软上限全部占满后，在该优先级的全部健康路由中按剩余硬并发容量分配，容量相同时轮询。

智能分组首次上游调用等待响应头最多 30 秒，同一成员重试等待最多 10 秒。

软上限只决定选路阶段；路由的配置硬上限保持原值，默认 50。硬上限小于软上限时仍以硬上限为准。没有延迟样本的路由先获得初始采样机会；延迟用 EWMA 更新，30 分钟未更新即过期。

选路、检查暂停状态、清理过期租约和占用容量在同一个 Redis Lua 脚本中完成，避免多个实例使用旧容量快照越过阶段或优先级。Redis Cluster 的所有调度状态使用同一 `{routes}` 哈希标签。脚本成本随候选路由数增长，同一槽仍受 Redis 的处理能力限制。

## 连续失败与暂停

- 健康状态分为路由级和模型级。模型级按「路由 ID + 实际上游模型 + API 协议」隔离，映射到同一目标的别名共享状态。默认连续 3 个完整模型请求最终失败后，只隔离该模型；同一个请求的首次调用及自动重试合并记 1 次，智能分组连续 3 个这样的请求（共 6 次调用）才隔离。
- 请求重试成功不累计失败，并清零已有连续失败。智能分组切换到其他成员前，只为已耗尽重试的成员记 1 次失败；不同成员各自记录路由健康状态。高并发下按请求完成顺序更新连续计数。
- 2xx 响应成功传输完毕且没有 JSON / SSE 错误才清零连续失败。5xx、429、普通 403、响应体截断、200 中的错误属于当前模型，不会暂停其他模型。明确的模型不存在 / 不支持错误立即隔离当前模型，不再执行无效重试；其他失败仍按 3 个完整请求计数。
- 没有 HTTP 响应的连接、传输错误、401 或明确的 Key 无效错误仍属于路由级；连续 3 个完整请求失败后暂停整条路由 30 分钟，每 3 分钟流式探测，成功或到期恢复。
- 客户端取消、下游连接断开和 400 / 422 参数错误不计入失败，也不清零已有失败。
- 智能分组选路会原子检查路由级暂停和当前模型隔离。当前模型所有候选都不可用时返回 503、`model_temporarily_paused`，错误信息明确只涉及请求模型；其他模型继续调度。路由级暂停返回 `route_temporarily_paused` 和 `Retry-After: 180`。本次模型的候选调用耗尽则返回 502、`model_upstreams_failed`，不再声称所有模型都失败。
- 暂停前已开始的请求可以完成；旧请求的成功或失败不能改变新一轮暂停或恢复状态。仍在暂停的路由停止后续自动重试。
- 路由级 30 分钟到期自动重新进入正常调度；失败探测不会延长本轮暂停。模型隔离必须经成功探测或成功手动测试恢复，不会因计时到期将已知失败模型重新交给用户请求。

健康状态、失败次数、探测计划和恢复版本保存在 Redis，重启服务后继续执行。同一路由的同一实际模型和协议在不同智能分组内共享隔离；一个模型失败不影响其他模型。健康状态采用 v2 命名空间，升级时不继承旧版无法区分故障类型的整路由失败计数和暂停；成员手动暂停和并发租约保留。

## 手动暂停成员与页面提示

智能分组的每个成员行提供“暂停 / 恢复”按钮。手动暂停只影响该智能分组内的这个成员，保存在 PostgreSQL，不影响其他分组或路由直接入口。页面点击“恢复”打开模型测试弹窗，成功后点击“恢复调度”才解除暂停。自动探测成功和服务重启都不会解除成员手动暂停。

手动暂停的成员从选路、模型可用容量汇总和对应成员恢复探测中排除，管理员仍能在成员列表中看见它。已开始的请求可以完成。页面每 10 秒刷新，显示自动暂停路由、手动暂停成员、隔离的具体模型 / 协议及下次探测时间；隐藏页面不轮询，并避免后台轮询重复并发。模型目录保留，管理员仍可选择隔离模型进行测试。异常模型默认展示首个名称和额外数量，展开显示完整模型、协议及下次探测时间；详情中的测试图标会预选对应模型或映射别名和协议。

上游管理卡片在桌面端（1280px 起）每行 6 个，中小屏按 4 / 3 / 2 / 1 列自适应。余额作为主指标，站点域名、连接状态和分组数量分层显示，操作保留图标入口和无障碍标签。

## 手动模型测试与恢复

路由行和智能分组成员行提供“模型测试”图标入口，下拉框完整展示路由已同步模型及可用映射别名，也可以选择“手动输入模型”，选择 Chat Completions、Responses、Anthropic Messages、Gemini 或 Embeddings 协议。模型列表可以手动刷新；成员测试和刷新使用这个成员的实际 Key、模型映射和路由出口代理，暂停的成员也能测试。返回测试是否成功、HTTP 状态和耗时，不向页面返回上游 Key 或错误正文。

测试执行一次非流式固定最小推理请求，响应头等待 30 秒，并校验完整 JSON 结果，不改变故障暂停或手动暂停。测试和模型刷新共享配置硬并发容量；每条路由同时只有一个手动测试或手动刷新任务，Redis 独占锁会随租约续期，后台自动探测的计划不受影响。

推理成功后产生 5 分钟有效、只能使用一次的恢复凭证，绑定管理员工作区、路由、成员分组、当前故障版本及被测试配置。新测试会清除这个范围的旧凭证；失败测试不发放恢复凭证。过期、配置或成员策略变更、新一轮故障暂停，以及其他路由或成员的凭证，都会拒绝恢复并提示重测。

点击“恢复调度”只清除被测试实际模型 / 协议的隔离，同时清除整条路由的连接 / 凭据故障暂停及当前分组成员的手动暂停；其他模型隔离和其他成员的手动暂停仍需分别恢复。凭证同时绑定路由及模型故障版本。恢复时锁定 PostgreSQL 的路由和成员配置，并在 Redis 中原子校验和消费凭证，旧业务请求、旧自动探测不能覆盖恢复后的状态。既有迁移 `000034_add_member_policy_revision` 用于识别成员策略再次变化，本次不增加数据库迁移。

## 恢复探测

模型隔离后在第 1、3、5、10 分钟探测，此后在第 20、30、40 分钟等时点探测。相邻计划间隔为 1、2、2、5、10 分钟，后续均为 10 分钟。计划锚定隔离开始时间，不叠加探测请求耗时；成功后立即恢复并清零阶梯。旧版未保存隔离开始时间的状态按修正后的相邻间隔继续，已安排的首次任务保留。若容量或工作池延迟导致下一时点已过，则从本次完成起等待对应间隔，避免连续补发探测。容量不足或成员手动暂停造成的跳过不累计探测失败。路由级故障保留每 3 分钟探测。后台每 5 秒检查到期任务；容量或工作池饱和时任务可能延后。每个实例使用 8 个工作线程，每个隔离模型通过 Redis 独占领取，正在执行的探测持续续约；实例退出后其领取过期，其他实例能够接管。

探测使用失败调用对应的模型和 API 协议，发送固定的最小请求，最多生成 16 个 token。只保留分组 ID、模型 ID 和接口路径，不保存或重放用户内容。临时 Key 仍经过创建及清理流程；预置 Key、模型映射和出口代理从当前路由或原智能分组成员配置重新读取。删除或停用的路由、分组或成员不会继续发送探测。

自动推理恢复探测采用流式：Chat Completions、Responses、Anthropic Messages 发送 `stream: true`，Gemini 使用 `streamGenerateContent?alt=sse`。仅收到 HTTP 200、心跳或起始事件不会恢复；必须读取有效 SSE 结果及对应协议的正常结束标记，错误事件、截断或超时均视为失败。为避免极小输出上限误判，Responses 因 `max_output_tokens` 正常停止也视为可用。模型列表、Embeddings 和 Compact 接口不支持流式，保留非流式 JSON 校验。

探测与业务请求共享路由的硬并发名额。探测上下文时限 45 秒，响应头等待 30 秒，流式响应最多读取 1 MiB；临时 Key 管理调用沿用原有 HTTP 超时，执行中持续续约独占领取。不自动重试模型请求。成功后立即恢复调度。实际模型探测会按上游规则产生少量用量。管理页面展示暂停截止时间和下次探测时间。

## 高并发与验证

延迟观察使用有界缓冲，每 500 毫秒汇总并批量写入 Redis；暂停判断实时写入。租约每 15 秒续约，45 秒过期，使用 Redis 时间避免实例间时钟偏差。释放操作可并发调用且只执行一次。

运行测试时使用独立 Redis 和 PostgreSQL，并设置 `MODEL_PROXY_TEST_REDIS_URL`、`MODEL_PROXY_TEST_DATABASE_URL`。不要指向生产实例。测试只清理自己创建的 Redis 状态和 PostgreSQL 测试 schema。

```powershell
$env:MODEL_PROXY_TEST_REDIS_URL='redis://127.0.0.1:26389/0'
$env:MODEL_PROXY_TEST_DATABASE_URL='postgres://postgres@127.0.0.1:26489/postgres?sslmode=disable'
go test ./...
```

覆盖了 5 / 10 / 硬上限阶段、低延迟优先、256 请求争抢容量、严格优先级、故障路由跳过、64 个并发探测领取、阶梯时间、旧请求及旧探测结果隔离、流式恢复及硬上限。额外验证直接入口和智能分组内一个模型连续 503 后其他 9 个模型仍正常，映射别名共用隔离而不同协议独立，200 中的 SSE 错误、模型不存在无效重试，以及手动恢复只清除被测模型。

PostgreSQL 集成测试执行模型代理迁移，验证成员手动暂停持久化、其他分组及直接入口隔离、工作区权限、可用容量变化，以及手动暂停与自动探测恢复的完整联动。

实现参考 [sub2api 的运行时延迟反馈调度](https://github.com/Wei-Shaw/sub2api/blob/main/backend/internal/service/openai_account_scheduler.go) 和 [熔断状态处理](https://github.com/Wei-Shaw/sub2api/blob/main/backend/internal/service/openai_proxy_stream_circuit.go)，软上限与优先级边界采用本项目的规则。
