# 智能分组调度

普通推理仍严格遵守成员优先级。同优先级内，先选择近期成功率正常的成员，再应用临时 Key 软限 5、预置 Key 软限 10 的顺序。临时 Key 用完后进入删除流程；近期连续失败或成功率低的临时成员不会挤占健康预置成员的优先机会。

成功率以一次成员请求为单位，在重试及完整响应结束后记录。一次失败后重试成功计为成功；HTTP 200 中的 JSON/SSE 错误仍计为失败；客户端取消和普通参数错误不计入健康评分。评分使用近期成功率的指数移动平均，低于 60% 或连续两个成员请求失败时降低调度优先顺序。这与“三个请求失败后自动暂停”的原有熔断计数互相独立。

同一健康层、同一软限层的成员采用平滑加权轮询，权重综合首响延迟、近期成功率、连续失败数和当前占用率。两类成员均达到软限后，仍按剩余硬容量和轮询分配。硬并发由每条路由的现有配置控制。

评分按实际映射后的模型与接口保存，别名共享目标模型评分；某个模型失败不会影响其他模型。明确的凭据错误可降低整条路由的偏好。“永不暂停”仍保持可调度，不创建新的暂停或恢复探测；健康成员容量用尽后可以使用这些低成功率成员。

评分和延迟通过有界队列每 200 ms 批量写入 Redis，评分 30 分钟后过期，不新增数据库表。选择与占位保持单次 Redis Lua 原子操作，不缓存剩余并发槽。删除路由同步删除评分；手动测试并恢复调度会清除对应评分，旧请求不能覆盖恢复后的状态。

单次启动等待上限仍为首次 90 秒、重试 60 秒，包含临时 Key 准备及首个有效流事件。401/403、无模型、普通请求错误及 429 不再重复请求同一成员；超时时如果还有候选成员则立即切换。整个分组在首响前共用 150 秒预算，避免逐成员累积数分钟等待。成功开始的流式响应不受首响预算限制。

Compact 继续跨优先级、跨关键词选择最近成功的成员，不新增自动探测。Embeddings 继续本地返回，不参与上游调度或恢复探测。
