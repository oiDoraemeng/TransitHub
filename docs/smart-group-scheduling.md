# 智能分组调度

普通推理严格遵守成员优先级。同优先级内，临时 Key（使用后删除）与预置 Key 统一评分、平滑加权轮询；不再按 Key 类型分层，也不再使用 5/10 并发软限。Key 的创建、删除流程不参与调度评分。每条路由仍按现有配置执行硬并发上限（例如 50）。

成功率以一次成员请求为单位，在重试及完整响应结束后记录。一次失败后重试成功计为成功；HTTP 200 中的 JSON/SSE 错误仍计为失败；客户端取消和普通参数错误不计入健康评分。评分使用近期成功率的指数移动平均。这与“三个请求失败后自动暂停”的原有熔断计数互相独立。

评分参考 [Sub2API](https://github.com/Wei-Shaw/sub2api/blob/main/backend/internal/service/openai_account_scheduler.go) 的成功率、首 Token 延迟、当前负载三个维度，基础权重分别为 0.8、0.5、1。首 Token 延迟采用同级最快成员与当前成员延迟比的平方根（最低 0.1，尚无采样为 0.5），避免极慢离群值掩盖快路由之间的差异；流式请求必须等到首个有效输出才计时，普通响应使用响应头耗时。负载按当前并发 / 配置硬上限计算。

基础分数为 `0.8 × 成功率 + 0.5 × 延迟因子 + (1 − 当前并发 / 硬上限)`；再乘以成功率平方和连续失败惩罚（每次减半，最低 0.02）。近期明确凭据错误另乘 0.02，最低最终权重 0.01。使用此权重平滑分配，同级健康路由都会获得流量，近期成功率高、首 Token 快、负载低的成员获得更多请求；硬容量耗尽或被暂停的成员不参与。选择与占位在同一次 Lua 中执行，多个实例共享实际负载。

评分按实际映射后的模型与接口保存，别名共享目标模型评分；某个模型失败不会影响其他模型。明确的凭据错误可降低整条路由的偏好。“永不暂停”仍保持可调度，不创建新的暂停或恢复探测，但低成功率时分配量会减少。

评分和延迟通过有界队列每 200 ms 批量写入 Redis，评分 30 分钟后过期，不新增数据库表。选择与占位保持单次 Redis Lua 原子操作，不缓存剩余并发槽。删除路由同步删除评分；手动测试并恢复调度会清除对应评分，旧请求不能覆盖恢复后的状态。

单次启动等待上限仍为首次 90 秒、重试 60 秒，包含临时 Key 准备及首个有效流事件。401/403、无模型、普通请求错误及 429 不再重复请求同一成员；超时时如果还有候选成员则立即切换。整个分组在首响前共用 150 秒预算，避免逐成员累积数分钟等待。成功开始的流式响应不受首响预算限制。

Compact 继续跨优先级、跨关键词选择最近成功的成员，不新增自动探测。Embeddings 继续本地返回，不参与上游调度或恢复探测。

实际发往 `dora2api.xyz` / `www.dora2api.xyz` 的 `gpt-6-luna`、`gpt-5.6-luna` 请求，在模型映射及协议转换之后强制使用上游 `max`。Responses 使用 `reasoning.effort`，Chat Completions 使用 `reasoning_effort`；Gemini 别名转换为 Chat 后同样适用。JSON 及 SSE 元数据返回客户端原始模型和推理强度，未指定强度时移除注入值，保留上游其余 reasoning 元数据。该覆盖不修改重试用的原始请求体，不作用于其他站点、模型或 Compact。
